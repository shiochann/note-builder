# note-builder｜有料ノート制作スキル

有料ノート（note / Brain）を **ヒアリング → 知識の統合 → 目次＋特典 → 本編（章ごと） → 核となる主張 → セールスレター** の順に作る。
途中で止めても `_state.md` に進捗が残るので、次回 `/note-builder` だけで続きから再開できる。

**このスキルは勝手に先へ進まない。** 各フェーズの最後に必ずユーザーの承認を取り、承認されるまで次のフェーズに入らない。

**本編は自由に書く。核となる主張はセールスレター専用。** 主張で本編の章立てや中身を縛らない。主張は本編が完成してから、本編に書いてあることを材料にして決める。

---

## 呼び出し形式

```
/note-builder                     ← 進行中のノートがあれば続きから。なければ新規
/note-builder <ノート名>           ← 指定したノートを新規作成 or 再開
/note-builder <ノート名> 第3章     ← 第3章を書く（または書き直す）
/note-builder <ノート名> レター    ← 主張→セールスレターを作る（本編完成後のみ）
```

---

## 生成物（ノート1本 = 1フォルダ）

```
<出力先>/<ノート名>/
  _state.md            ← 進捗と決定事項。毎フェーズ終了時に更新する
  00_ヒアリング.md      ← ヒアリングの回答をそのまま記録
  01_domain.md         ← 既存ファイル＋ヒアリングを統合した知識（本編の材料）
  02_企画書.md         ← 特典・目次・図解のざっくり配置
  03_図解計画.md       ← 図解の指示書一覧（章・番号・種類・要素・キャプション）
  10_本編.md           ← 本編。章ごとに生成してこのファイルに追記する。これをそのまま貼る
  11_主張.md           ← セールスレターの核となる主張。本編完成後に作る
  12_セールスレター.md  ← 最後に作る
```

**本編はファイルを分けない。** 章ごとに生成するが、書く先は常に `10_本編.md` の1ファイル。

### 出力先の決め方

1. 呼び出し時にパスの指定があればそれを使う
2. なければカレントディレクトリに `<ノート名>/` を作る
3. `_state.md` があるフォルダが見つかれば、そこを再開対象にする

---

## 開始時の手順（毎回）

1. `_state.md` を探す。あれば読んで、`現在のフェーズ` から再開する
2. なければ新規として **フェーズ1** から始める
3. 再開時は「前回ここまで進んでいます。続けますか」と一言確認してから進む

---

## フェーズ1｜ヒアリング

`references/01_interview.md` の質問票を使う。**一度に聞くのは3〜5問まで。** 全部を一気に投げない。

聞く順番は固定：

1. **基本**：プラットフォーム（note / Brain）、ノートの仮名、想定価格帯、文体
2. **特典**：すでに決まっているか。決まっていれば内容と配布形式を先に聞く
3. **既存ファイル**：知識をすでにまとめたファイルがあるか。パスを聞いて **全部読む**
4. **読者**：誰に、今どんな状態で、読み終えたらどうなっていてほしいか
5. **ドメイン深掘り**：実績と数字、失敗談、独自の手順、よくある誤解、他教材との違い

特典を先に聞く理由：本編のどこで特典に繋げるかを、知識の整理段階から織り込むため。

回答は `00_ヒアリング.md` に **要約せずそのまま** 追記する。数字・固有名詞・言い回しは本編とレターでそのまま使う材料になる。

**承認ゲート**：「知識として足りない部分はこれです」と欠けを提示し、追加で聞くか進むかをユーザーに決めてもらう。

---

## フェーズ2｜domainの統合

`00_ヒアリング.md` と既存ファイルを統合して `01_domain.md` を作る。

構成：

```
# domain｜<ノート名>

## 読者
（誰に・今の状態・読後の状態）

## 実績と数字
（出典つき。ヒアリングで出た数字だけ。推測で足さない）

## 主要な知識
（テーマごとに見出しを切る。手順は手順として、主張は主張として分ける）

## 失敗談・つまずき
（本編の説得力になる。具体的に）

## よくある誤解・反論
（レターの「敵の設定」と本編の反論回収に使う）

## 特典
（内容・形式・本編のどこと繋がるか）

## 未確認・要記入
（数字が曖昧なもの、裏取りが必要なもの）
```

**ルール**
- 既存ファイルに書いてあることは丸写しではなく、この構成に **並べ直す**
- 数字は「ヒアリングで出たもの」だけ。埋まらない数字は `【要記入】` にする
- 既存ファイルと回答が矛盾したら、どちらが正しいかユーザーに聞く

**承認ゲート**：`01_domain.md` を提示し、抜け・間違いを直してもらう。

## フェーズ3｜目次＋特典案＋図解のざっくり配置

`references/03_toc-patterns.md` に沿って目次を作る。**ここでは主張を持ち込まない。** 読者が理解しやすい順、手を動かしやすい順で組む。

**目次の原則**
- 序章 → 本編 → 終章。本編の章の並びは **読者の理解の順番**（問題 → 原因 → 解決 → 手順 → 応用）
- 各章に「この章で読者ができるようになること」を1行つける
- 有料ラインの位置を明示する（序章末尾 or 第1章の途中が基本）
- 章数は5〜8。10を超えたら統合する
- ユーザーが「この章を入れたい」と言ったものは、理由を問わず入れる

**特典案**
- 特典が未定なら、本編を読んだ読者が手を動かすときに欲しくなるものを3案出す（テンプレ・チェックリスト・スキル・記録の公開など）
- 決まっていれば、本編のどの章の末尾で案内するかを目次に書く

**図解のざっくり配置**
- この段階で「どの章に何枚くらい、何の図解か」を仮置きする（章ごとに1〜3枚）
- 詳細はフェーズ4で章を書くときに確定する

目次のフォーマットは `templates/企画書.md` に従う。`02_企画書.md` に書き込む。

**承認ゲート**：目次の修正はここで受ける。修正が入ったら `02_企画書.md` を直し、再提示する。確定するまで本編に入らない。

---

## フェーズ4｜本編（章ごとに生成、1ファイルに追記）

### 進め方

1. **1回の呼び出しで書くのは1章だけ。** 序章から順に進める
2. 書く前に `01_domain.md` の該当部分と `02_企画書.md` の目次を読み直す
3. 章を書いたらユーザーに提示する
4. 承認されたら `10_本編.md` に **追記** する（初回は新規作成）
5. 修正指示が来たら、その章だけ書き直して提示する
6. `_state.md` の `完了した章` を更新する

### 10_本編.md の構造

```
（有料ラインより前：序章など）

=====ここから有料=====

# 第1章　○○
## 1-1　○○
...

【図解1｜フロー図】毎朝の流れ

...

# 第2章　○○
```

- 章タイトルは `#`、節は `##`、小節は `###`。それ以上は使わない
- `=====ここから有料=====` は貼るときに削除する目印。位置は `02_企画書.md` の通り
- 章と章のあいだは空行2つ。区切り線は入れない（貼ったとき二重になるため）

### 章の中身のルール

- 冒頭に **この章で何ができるようになるか** を2〜3行
- 末尾に **次の章への橋渡し** を1〜2行
- 数字は `01_domain.md` にあるものだけ。ないものは `【要記入：○○】`
- 記法は `references/05_platform-rules.md` に従う（表は使わない・ネストは1段まで・太字は1段落に1箇所）
- 1文は短く。スマホで読む前提で改行を多めに
- 文体は `_state.md` の `文体` に従う（敬体/常体・一人称）
- 主張を意識して書かない。読者に役立つことを、その章で一番伝わる形で書く

### 図解を入れる（章を書くのと同時）

`references/04_diagram-types.md` に沿って、章を書きながら図解の位置を決める。

**入れる目安**：手順・比較・全体像・Before/After・関係性が出てきたら入れる。1章に1〜3枚。

本文には目印だけを置く：

```
【図解3｜比較図】手動運用と自動運用の1日
```

同時に `03_図解計画.md` に指示書を追記する：

```
## 図解3｜比較図｜手動運用と自動運用の1日
- 章：第2章 2-1
- 種類：比較図（左右2列）
- 入れる要素：
  - 左：手動運用（朝ネタ探し→執筆→投稿→数字を見る、所要90分）
  - 右：自動運用（朝は確認だけ、所要5分）
- キャプション：同じ「毎日投稿」でも、人がやる部分がここまで減る
- サイズ：横長 1280×720
- 備考：時間の数字は【要記入】
```

図解の番号はノート全体で通し番号。目印は画像に差し替えるまで本文に残す。

### 章を書き直すとき

`10_本編.md` の中で `# 第N章` から次の `# ` までを、その章の範囲として **置き換える**。他の章は触らない。
図解番号がずれる場合は `03_図解計画.md` も合わせて直す。

### 承認ゲート（章ごと）

「この章でOKなら次の章に進みます」と聞く。OKが出るまで次の章を書かない。
全章完了したら「本編が揃いました。次はセールスレターの核となる主張を決めます」と伝える。

## フェーズ5｜核となる主張（セールスレター専用）

**本編が全章完成してから** 作る。主張は本編を縛るものではなく、**完成した本編を売るための一本の線**。

`10_本編.md` と `01_domain.md` を読み直し、`references/02_claim-patterns.md` の型から候補を **3つ** 出してユーザーに選んでもらう（混ぜてもよい）。

主張のフォーマット（`11_主張.md`）：

```
# 主張｜<ノート名>

## 一文で
「○○だけでは△△になる。だから□□が必要」

## 根拠（3つ）
1.
2.
3.
（それぞれ、本編のどの章に書いてあるかを添える）

## 想定される反論と回答
- 反論：
  回答：（本編のどこで答えているか）

## 読者が最後に取る行動
（このノートを読み終えた読者が、翌日やること）

## 敵と味方
- 敵：（読者を今の状態に留めているもの。人ではなく「やり方」を敵にする）
- 味方：（このノートが勧めるやり方）
```

例：「Threadsだけだと垢バンで全部消える。だからXも同時に育てる必要がある。だからXの伸ばし方を知る必要がある」

**チェック**（すべてYESになるまで直す）
- 主張は一文で言えるか
- 読者の悩みから始まっているか（作者の言いたいことから始まっていないか）
- 根拠は **本編に実際に書いてあること** か（本編にないことを主張の根拠にしない）
- 特典は主張の「実行手段」として説明できるか
- 根拠の少なくとも1つは作者の実体験・数字か

**承認ゲート**。

---

## フェーズ6｜セールスレター

`11_主張.md` が承認されてから作る。`references/06_letter-structure.md` の骨格に沿って `12_セールスレター.md` を書く。

**ルール**
- 敵の設定は `11_主張.md` の「敵と味方」と一致させる
- 商品の中身の説明は **完成した `10_本編.md` の実際の見出し** から書く
- 数字は `01_domain.md` のものだけ。ないものは `【要記入】`
- 特典の説明は本編のどこと繋がっているかが分かるように書く

**ロジックチェック**（レター末尾に「制作メモ（公開時は削除）」として付ける）

```
| 主張の要素 | レターのどこで回収したか | 本編のどこが裏づけか |
|---|---|---|
| 一文の主張 | | |
| 根拠1 | | |
| 根拠2 | | |
| 根拠3 | | |
| 反論と回答 | | |
| 敵の設定 | | |
| 読者が取る行動 | | |
```

空欄があれば、レターに戻って埋める。本編に裏づけがない要素は、主張のほうを直す。埋まるまで完成としない。

**承認ゲート**：提示して修正を受ける。

---

## _state.md の更新

各フェーズの承認が出た直後に `templates/_state.md` の形式で更新する。書く内容：

- 現在のフェーズ
- 決定事項（プラットフォーム・ノート名・文体・価格帯・出力先）
- 完了した章 / 残りの章
- 図解の最新番号
- 次にやること（1行）

---

## やってはいけないこと

- 承認なしに次のフェーズへ進む
- 一度に複数の章を書く
- 本編を章ごとに別ファイルにする
- ヒアリングにない数字や実績を作る
- 既存ファイルを丸写しにする（並べ直して、ノートの文体で書く）
- 表を本文に入れる（図解に回す）
- 主張で目次や本編を縛る（主張はレター専用）
- 本編が終わる前に主張やレターを作る（ユーザーが明示的に望んだ場合を除く）
- 本編に書いていないことを主張の根拠にする
